# Open questions

Agents append here when a spec is silent or contradictory. Format: `- [task id] question. Proposed default: ... (status: open/answered)`.

- [G0] Is 16 the correct minimum age (digital-consent age in Poland)? Proposed default: 16. (status: open)
- [G0] FR-P2 versus injuries: a main muscle group fully blocked by an injury is skipped and reported, not an error (algorithms.md 4.3). (status: open, confirm)
- [D-05] The Hugging Face model weights could not be verified when this package was written; run the feasibility check before any AI code. (status: open)
- [B-02] Refresh-token lifetime under rotation: does each rotated token get a fresh 30 days (sliding), or does the family keep the 30 days from login (absolute)? Proposed default: sliding, implemented that way. (status: open)
- [B-02] Rate limiting and lockout numbers are not specified (D-06 not written yet). Proposed default: 10 requests per 60 s per client IP and route on register/login (later forgot), 429 `rate_limited` with `Retry-After`; no per-account lockout (it lets an attacker lock out a victim). Configurable via `AUTH_RATE_LIMIT`, `AUTH_RATE_WINDOW_SECONDS`. (status: open)
- [B-02] bcrypt cost factor not specified. Proposed default: 12 (`BCRYPT_ROUNDS`). (status: open)
- [B-03] Logout with a refresh token that belongs to another user or is unknown: the contract lists only 204/401. Proposed default: 401 `unauthorized`, nothing revoked; the caller's own token (even already rotated) revokes its whole family and gives 204. (status: open)
- [B-03] Access tokens stay valid until expiry (max 15 min) after logout; only refresh tokens are revoked. Proposed default: accept this (stateless JWT, no deny list). (status: open)
- [DB-03] The spec fixes only the ten muscle groups (algorithms.md section 3). The injury types (17, with average healing days), allergens (EU 14 plus lactose) and food categories (16) are my proposed defaults in `database/seed/00{2,3,4}_*.sql`. Proposed default: keep them; extend through new seed rows, names are the idempotency key. (status: open)
- [DB-03] `injury_type_excluded_exercise` rows need exercise ids, so they are seeded with the exercises in DB-04, not in DB-03 as docs/agents/data.md lists them. Proposed default: DB-04. (status: open)
- [DB-04] The exercise list (112), their descriptions/instructions, secondary muscle groups and the per-injury exclusions in `database/seed/005..007_*.sql` are my drafts; a human must spot-check a sample (docs/agents/data.md, step 6), especially the injury exclusions, which are conservative proposals and not medical advice. Proposed default: keep until reviewed. (status: open)
- [DB-04] Equipment tiers: a pull-up bar, bench, dumbbells and bands count as `home`; chairs, walls and towels count as `none`. Pull-ups are therefore `home`, not `none`. Proposed default: as seeded. (status: open)
- [DB-05] Nutrition values in `database/seed/008_foods.sql` (about 210 foods, 88 of them mapped to Food-101 labels) were entered from memory in the style of USDA FoodData Central and `nutritional_database.json` was not used (D-05 has not verified it). A human must spot-check a sample against FoodData Central; dish values and especially dish allergens are recipe averages and safety relevant (FR-N3). Proposed default: keep until reviewed. (status: open)
- [DB-05] "kcal roughly 4P + 9F + 4C within 10 %" is too strict for high-fibre and dried foods. Proposed default used by `scripts/validate_seed.py`: tolerance max(12 % of kcal, 15 kcal). (status: open)
- [DB-05] 13 Food-101 labels have no food row yet and are listed in `database/seed/food101_unmapped.txt`; which labels the team keeps depends on D-05 (model choice). Proposed default: keep the file as the explicit list of gaps. (status: open)
- [B-08] `GET /exercises/{id}/alternatives` needs the user's level, equipment and injuries (algorithms.md 4.9), but the contract does not say what happens for a user who has no profile yet. Proposed default (implemented): without a profile no level/equipment restriction applies (treated as advanced/gym) and only the injury rule filters; injuries are read from the `injury` table regardless. (status: open)
- [B-08] Order of the alternatives list is not specified. Proposed default (implemented): compound exercises first, then by name. List endpoints (`/exercises`, `/foods`) are ordered by name, then id. (status: open)
- [B-09] Inactive foods (`is_active = false`) are hidden from the list and the detail endpoint (404). Proposed default: as implemented. (status: open)
- [B-06] Contract versus schema: the API offers PAL 1.375 and 1.725 (algorithms.md section 0) but `user_profile.activity_level_pal` was `numeric(3,2)`. Resolved by migration 0002 (`numeric(4,3)`, `schema_postgres.sql` updated); the API now stores and computes with the exact value. (status: answered, needs APP/DATA acknowledgement in the PR)
- [B-06] The contract does not limit the number of injuries or the start date. Proposed default (implemented): no limits; any ISO date is accepted. (status: open)
- [B-06] `GET /users/me/injuries` order is not specified. Proposed default (implemented): active first, then newest start date. (status: open)
- [B-06] `excluded-foods` and `allergies` replace the whole list (PUT); duplicate ids are dropped; an unknown or inactive id is a 422 with `details[].code = not_found` and nothing is changed. (status: open)
- [B-11] `TrainingPlan.name` is required by the contract but no rule defines it. Proposed default (implemented): `"<Goal>, <n> day(s) per week"`, for example "Muscle gain, 4 days per week". (status: open)
- [B-11] Shape of `details` in the 422 `insufficient_exercises` answer (the contract says only "listing the groups and the suggestions"). Proposed default (implemented): one entry per empty group `{field: "muscle_group", code: "no_eligible_exercise", muscle_group: "<name>"}`, then `{code: "change_equipment", equipment: "<tier>"}` and `{code: "change_goal", goals: [...]}` when a suggestion exists. APP must read these keys. (status: open)
- [B-11] When every required group is blocked by injuries there is nothing to train safely. Proposed default (implemented, domain behaviour): 422 `insufficient_exercises` with the blocked groups as `no_eligible_exercise` and no suggestions. (status: open)
- [B-11] Accepting a plan that is not a draft (already active or archived) is a 409 `conflict`; accepting a missing or another user's plan is a 404. A failed generation (422) keeps the previous draft. `start_date` may be any date, `end_date = start_date + 56 days` (algorithms.md 4.8, constant PLAN_DURATION_DAYS). (status: open)
- [B-13] A swap is checked against the plan's own level and equipment (the snapshot stored with the plan) and the user's current active injuries. `GET /exercises/{id}/alternatives` (B-08) uses the profile instead, so for a plan generated with a level or equipment override the list can offer an exercise that the swap refuses with `invalid_swap` (`above_level` or `needs_equipment`). Proposed default: as implemented; if APP needs the lists to agree, add an optional plan or session-exercise parameter to the alternatives endpoint (contract change). (status: open)
- [B-13] `invalid_swap` details: `{field: "exercise_id", code: <reason>}` with reason one of `unknown_exercise`, `same_exercise`, `other_muscle_group`, `already_in_session`, `above_level`, `needs_equipment`, `excluded_by_injury`. Swapping back to the generated exercise clears `original_exercise_id`. (status: open)
- [B-13] Editing or swapping an exercise of an archived plan is a 409 `conflict`; draft and active plans can be changed. `PATCH /session-exercises/{id}` has no backlog task of its own; implemented here with B-13. `planned_weight_kg` is limited to 0-9999.99 (column precision). (status: open)
