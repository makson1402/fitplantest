## B-22 (meal suggestions)
- Decision: the plan repeats every 7 days from `start_date`; today's plan day is `((date - start_date) mod 7) + 1`, so a plan older than 7 days offers the meals of the matching day (algorithms.md 5.3 says "7 days", not what happens after).
- Decision: a planned meal counts as eaten when a live nutrition log of that day has `planned_meal_id` set to it; it is then not suggested again.
- Decision: planned meals whose foods are no longer allowed for the user (an allergy or exclusion added after the plan was made, or an inactive food) are not offered, so the "never an allergen" guarantee holds for old plans too.
- Decision: `remaining` in the answer is never negative (a day over the target shows 0); the ranking itself uses the raw difference.

## B-26 (scheduler and push)
- Decision: instead of one cron trigger at exactly Monday 07:00 per time zone, one scheduler process runs idempotent jobs every 15 minutes. A user's report for the previous Monday-Sunday is created by the first pass after their local Monday 07:00 (so a job that was down catches up). `UNIQUE (user_id, report_type, period_start, period_end)` plus insert-if-absent make repeated and concurrent runs a no-op, as the task requires.
- Decision: the notification row is the push queue (`sent_at IS NULL`). A crash between creating and pushing loses nothing; an unreachable Expo service is retried for 24 h; users without registered devices simply get the inbox entry. `PUSH_ENABLED=false` turns delivery off.
- Decision: the weekly report is also created for a week without any records, as long as the user has 7 days of history overall (algorithms.md 12 says "if the minimum-data rule holds"); its metrics are then null.
- Decision: expired-photo cleanup never deletes without MongoDB configured (it cannot know which photos are still referenced). `PHOTO_DIR` is written by B-19; until then the job finds nothing.
- Note: the achievement and motivational notification types have no producer yet; the dispatch job already delivers any notification row.

## B-27 (sync endpoints)
- Decision (D-07 reading): workouts and nutrition logs are append-only in sync, as D-07 says: they can be created and deleted; sending a stored one again with no `base_updated_at` is a retry (`unchanged`), with a `base_updated_at` it is an edit and a `conflict` (the server copy comes back). Body measurements can be edited. The REST routes `PUT /workouts/{id}` and `PATCH /nutrition-logs/{id}` still edit online; their changes reach other devices through pull. Tell me if the app needs offline edits of logs; that needs a rule for what a conflicting edit of a log means.
- Decision: a measurement is `unchanged` when its values equal the stored ones (a retry, also after the edit was applied), a `conflict` when it differs and `base_updated_at` is null or not the stored `updated_at`, otherwise it is applied. A new `client_uuid` for a day that already has a live measurement is a `conflict` with that measurement as `server_copy` (one measurement per day); the app drops its own item and adopts the copy (its `client_uuid` differs from the one it sent).
- Decision: a deleted item stays deleted. Re-sending its `client_uuid` as a live item is a `conflict` whose `server_copy` has `deleted_at`; deleting a deleted or unknown item is `unchanged`; a delete with a stale `base_updated_at` is a `conflict`, one without `base_updated_at` is applied.
- Decision: each item is its own transaction and a validation failure is `rejected` with the contract's Error body (`details[].field` relative to the item); at most 200 items per push request (422 above), the body limit of 1 MiB applies.
- Decision: pull orders all three kinds by (`updated_at`, kind, id); `limit` counts all kinds together. The cursor of the last page of a catch-up is `now - 60 s` (the overlap of the contract), so the client sees items from the last minute again and must apply them idempotently. `updated_at` is the start time of the writing transaction, which is why a late commit can carry an older time.
- Note: the `cursor` of a push response has the pull-cursor format (`now - 60 s`). An app that already has a pull cursor must keep its own; the push cursor is only useful as a first cursor for a fresh install that pushed before it ever pulled.
- Note: synced workouts update personal records but never adapt the plan (contract text); the profile weight follows the newest synced measurement like the REST route.
